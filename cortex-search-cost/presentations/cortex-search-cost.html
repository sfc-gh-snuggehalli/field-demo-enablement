The Cost Challenge at Scale

Serving Scales with Corpus Size

Serving cost is proportional to indexed data (rows x vector bytes + payload). A 262M-row corpus at 1,536 dimensions can reach 12K+ credits/month in serving alone.

Accidental Full Rebuilds

CREATE OR REPLACE on the service or source table forces a full re-index. At scale, this means re-processing every row and rebuilding the entire search index.

Lack of Cost Visibility

Without querying the right views, teams cannot separate serving vs. embedding vs. warehouse refresh costs, making optimization guesswork.

Idle Serving Waste

A running service incurs serving credits per GB of indexed data even when nobody is querying it. Dev/staging services left running accumulate silently.

Pattern: Chunks and vectors land in a standard table via MERGE or INSERT. The Cortex Search Service reads the table with TEXT INDEXES (keyword) + VECTOR INDEXES (BYO vectors) and refreshes incrementally. No Snowflake embedding cost is incurred for user-provided vectors.

How BYO Embeddings Work in Multi-Index Search

User-provided vectors skip EMBED_TEXT entirely

BYO Vectors (Zero Embedding Cost)

CREATE CORTEX SEARCH SERVICE my_svc
  TEXT INDEXES (chunk_text)
  VECTOR INDEXES (embedding)
  PRIMARY KEY (chunk_id)
  ATTRIBUTES doc_type, category
  WAREHOUSE = my_wh
  TARGET_LAG = '1 hour'
AS (SELECT * FROM document_chunks);

A bare column name in VECTOR INDEXES means user-provided. Snowflake indexes the vectors as-is. EMBED_TEXT = 0 credits

Managed Embeddings (Snowflake Runs EMBED_TEXT)

CREATE CORTEX SEARCH SERVICE my_svc
  TEXT INDEXES (chunk_text)
  VECTOR INDEXES chunk_text
    (model='snowflake-arctic-embed-l-v2.0')
  ATTRIBUTES doc_type, category
  WAREHOUSE = my_wh
  TARGET_LAG = '1 hour'
AS (SELECT * FROM document_chunks);

Specifying model= tells Snowflake to compute embeddings. EMBED_TEXT credits per token

Key insight: With BYO embeddings, the CORTEX_SEARCH_DAILY_USAGE_HISTORY view shows CONSUMPTION_TYPE = 'EMBED_TEXT_TOKENS' with 0 credits. You pay only for serving and warehouse refresh. At query time, you must provide a query vector (or set query_model for managed query embedding).

What Enables Incremental Refresh

  • PRIMARY KEY (chunk_id) on the service
  • REFRESH_MODE = INCREMENTAL (default)
  • Change tracking enabled on source table (auto-enabled)
  • Source data updated via INSERT / MERGE (not CREATE OR REPLACE)

FULL_INDEX_BUILD_INTERVAL_DAYS

Periodic compaction merges fragmented index segments into one optimized index. This does NOT re-embed unchanged data. Default is 1 day. Increase to reduce compaction frequency for large, low-churn corpora.

ALTER CORTEX SEARCH SERVICE my_svc SET FULL_INDEX_BUILD_INTERVAL_DAYS = 7;

Anti-patterns that force a full rebuild: (1) CREATE OR REPLACE on the service or source table. (2) Changing the source query schema (adding/removing columns). (3) Dropping and recreating the base table (loses change tracking). Always use ALTER and incremental DML instead.

The biggest cost lever is indexed data size. Vectors dominate: at 1,536 dims, each row contributes 6,144 bytes of vector data alone. Reducing dimensions (768 vs. 1,536) or archiving stale documents directly lowers the serving bill.

Cost Monitoring Queries

Separate serving, embedding, and warehouse costs per service

-- Daily cost breakdown by service and type
SELECT
    USAGE_DATE,
    SERVICE_NAME,
    CONSUMPTION_TYPE,
    CREDITS
FROM SNOWFLAKE.ACCOUNT_USAGE.CORTEX_SEARCH_DAILY_USAGE_HISTORY
WHERE USAGE_DATE >= DATEADD('day', -30, CURRENT_DATE())
ORDER BY USAGE_DATE DESC, SERVICE_NAME;

CONSUMPTION_TYPE Values

  • SERVING — per-GB/mo indexed data (always-on)
  • EMBED_TEXT_TOKENS — per-token embedding (0 for BYO)
  • BATCH — batch search query cost

DESCRIBE for Indexed Bytes

DESCRIBE CORTEX SEARCH SERVICE my_svc;
-- Check: BILLABLE_BYTES,
-- NUM_SHARDS, INDEXING_STATE,
-- SERVING_STATE
Pro tip: Use a dedicated warehouse per Cortex Search service during cost baselining. This isolates warehouse refresh credits from other workloads. Move to a shared warehouse once you have a cost baseline.

Optimization Levers

Operational levers first — no data changes required

1. AUTO_SUSPEND Serving

Suspend serving compute after idle periods. At 361 cr/day, even 8 hours of overnight suspension saves ~120 cr/day (~3,600 cr/mo). Minimum 30 min. Auto-resumes on next query.

ALTER CORTEX SEARCH SERVICE my_svc
  SET AUTO_SUSPEND = 1800;

2. Suspend Serving / Indexing Manually

For maintenance windows or off-hours with predictable schedules, manually suspend serving (stops billing) or indexing (stops refresh cost). Resume when ready.

ALTER CORTEX SEARCH SERVICE my_svc
  SUSPEND SERVING;
-- or: SUSPEND INDEXING

3. Increase TARGET_LAG

If new data is only added monthly, set target lag to match. This reduces warehouse refresh frequency from hourly to daily or longer.

ALTER CORTEX SEARCH SERVICE my_svc
  SET TARGET_LAG = '1 day';

4. FULL_INDEX_BUILD_INTERVAL_DAYS

For large, low-churn corpora, increase the compaction interval (default 1 day). This does not re-embed data — it only compacts fragmented index segments.

5. Verify Incremental Refresh

Confirm your service is actually refreshing incrementally and not silently doing full rebuilds. Use CORTEX_SEARCH_REFRESH_HISTORY to check.

SELECT REFRESH_ACTION, COUNT(*)
FROM TABLE(INFORMATION_SCHEMA
  .CORTEX_SEARCH_REFRESH_HISTORY(
    NAME => 'MY_SVC'))
GROUP BY REFRESH_ACTION;

6. Archive / Reduce (If Open to It)

Archive stale documents or reduce vector dimensions (768 vs 1,536). These directly cut indexed data size. Evaluate quality trade-offs first.

Important: Serving cost is proportional to indexed data size and independent of query volume. Reducing queries does not reduce the serving bill. The levers above (1-4) reduce cost without changing your corpus.

Next Steps

1. Audit Refresh Behavior

Run CORTEX_SEARCH_REFRESH_HISTORY on your production service. Confirm every refresh shows REFRESH_ACTION = 'INCREMENTAL', not 'FULL'.

2. Baseline Your Cost

Query CORTEX_SEARCH_DAILY_USAGE_HISTORY. Confirm EMBED_TEXT_TOKENS = 0 for BYO services. Validate serving credits match the formula.

3. Enable AUTO_SUSPEND

Set AUTO_SUSPEND = 1800 on all services with idle windows. For 361 cr/day, 8h overnight suspension saves ~3,600 cr/mo.

4. Match TARGET_LAG to Data Cadence

If new data arrives monthly, a 1-hour lag over-refreshes. Increase to match your actual data arrival pattern.

Cortex Search with BYO embeddings gives you hybrid search quality (keyword + semantic + reranking) with zero embedding cost and predictable, corpus-proportional serving costs. The key is: use PRIMARY KEY, keep refresh incremental, and monitor with the Account Usage views.
