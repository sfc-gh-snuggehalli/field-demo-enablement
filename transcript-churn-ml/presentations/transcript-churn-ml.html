The hybrid most teams end up with

Transcripts in one place, models in another

Calls land in the warehouse; topic models, churn models and LLM calls run on a separate ML platform, so features go out and scores come back every day.

"Untested on Snowflake runtimes"

Density clustering and survival libraries are assumed to need their own containers, so the whole churn workflow defaults to the external platform.

PII rides along

Raw transcripts carry names, phone numbers and emails. Every copy to an embedding service, a notebook or a bucket is another place to govern.

Topics drift, names don't

Re-clustering renumbers topics, so dashboards and features built on "cluster 7" silently change meaning.

Pattern: mask the raw text, redact each new segment once, embed redacted text only; topics, sentiment and churn features read the redacted layer; models are versioned and score where the rows are.

Where each step runs

SQL Declarative and incremental

Segmenting, AI_EMBED, similarity to exemplars, sentiment, the semantic view. Dynamic tables keep them fresh one new row at a time.

Warehouse Python Channel packages

umap-learn, hdbscan, lifelines, scikit-survival from the Snowflake package channel: stored procedures that fit, register and score.

Container Runtime Anything on PyPI

Packages outside the channel, GPUs, or long training runs: notebooks and ML Jobs install from the PyPI artifact repository.

Keep outside Only with a reason

A step that needs a system Snowflake cannot reach. Each one is a boundary crossing to secure and to pay for.

In this lab every step runs in the first two boxes; the third is the path for packages outside the channel.

AI_REDACT input + output token limit: why segmentation comes first
AI_REDACT is best effort. In one build it missed 2 staff names in 1,227 segments, so a deterministic pass removes known names (the rep list) after it. Embeddings are built only from the result.

A new month costs only the new month

January's calls are appended to the raw tables. The segment dynamic table recomputes only the affected calls; a stream hands only the new segments to AI_REDACT; the embedding dynamic table inserts only those rows.

Business topics first, then the ones nobody defined

Seeded (SQL)

Eight business topics, two exemplars each in the team's words. A segment takes a topic when its best cosine similarity is at least 0.47 and beats the runner-up by 0.03.

75% of segments, 98% correct; 1,925 × 16 similarities in under 2 seconds.

Discovered (warehouse Python)

UMAP to 5 dimensions, then HDBSCAN on the 25% left over. A topic needs about a tenth of the leftovers; smaller groups stay noise.

Both hidden topics found: AI writing requests (Jaccard 0.88) and seat sharing (1.00).

An LLM names each new cluster from six of its most typical redacted remarks: 4 calls for 252 leftover segments, written to a review queue as PENDING.

Why density clustering and not k-means

k given
k-means needed the cluster count HDBSCAN found
On clean synthetic text the two are about equally pure (96.4% vs 95.7%). The difference is the forced assignment: on real calls, small talk and cross-talk land in a topic's member list, its name and its feature.

The clusterer is a versioned model

The fitted UMAP + HDBSCAN pair is a custom model in the Model Registry with one input, the 1,024-value embedding (a model method takes at most 500 arguments, so the vector is one array column). Each version names its training snapshot.

V2, refit with January, kept both emerging topics: member overlap with V1 of 1.00 and 0.73. The mapping lives in ML.TOPIC_VERSION_MAP, so a reviewed name follows its topic.

Call signals are features, next to usage

ACCOUNT_USAGE_FV

Logins and reports over three months, the trend against the three before, seats, tenure, plan value. Computed from raw usage events.

ACCOUNT_CALL_SIGNALS_FV

Calls, negative price remarks by driver, segments in discovered topics, renewal talk, over the 90 days before each date.

Both are managed feature views over a static snapshot calendar: the same definitions read at four dates (negative price remarks per account 0 → 0.051 → 0.087 as calls arrive). Training is a point-in-time Dataset as of the snapshot, usable by any trainer inside Snowflake or out.

lifelines (Cox) and scikit-survival (gradient-boosted) ran in a warehouse stored procedure, six runs under Experiment Tracking. On ranking, logistic regression is a strong baseline; survival adds the probability of cancelling by any date and handles accounts still active at the end of follow-up. The Cox version is the registry default, scores 7,927 account-dates from SQL in 14 seconds, explains each account (top driver: negative price remarks), and has a model monitor.

The data-gravity ledger

Round trip

Training and scoring rows to the client with to_pandas, a model trained and scored there, scores back with write_pandas.

4,000 rows (60,000 feature values) out, 2,000 back, 2 boundary crossings.

In place

The registered model's PREDICT in SQL on the scoring table.

0 rows out, 0 back, 0 crossings.

Each path runs under its own query tag, so the same queries size an existing loop from ACCOUNT_USAGE. At 2,000 rows the round trip was faster (5.2 s vs 12.6 s); the point is the rows moved and the copies to govern, which grow with every account and every day.

Spend and PII controls

Estimate first

AI_COUNT_TOKENS before a full pass: 260,873 input tokens to embed every segment here.

Process each row once

Incremental dynamic tables and streams; filters before models; an LLM per cluster (7 calls) rather than per segment (737).

Cap and watch

Per-user AI quotas with block enforcement, custom budgets on the pipeline's warehouse, CORTEX_AI_FUNCTIONS_USAGE_HISTORY by query tag.

Govern the text

Masking on the raw column, redaction before embedding, embeddings only from redacted text, an embed-model column for planned re-embeds.
