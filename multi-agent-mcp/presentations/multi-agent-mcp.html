Every AI client wants your governed data

One connector per client

Claude, ChatGPT, Cursor and in-house assistants each want their own integration, credentials and copy of the business logic.

Governance in the prompt

"Only answer for EMEA" in a system prompt is a suggestion, not a control. A different client or a clever question walks around it.

Domains owned by different teams

Sales and support data have different owners, models and instructions. One giant agent flattens all of that.

No single audit trail

When the logic lives in each client, nobody can say who asked what, which agent answered, and what data it used.

The goal: any MCP client, one front door, and an answer per person decided by grants, not by the client or the model.

Architecture

A Snowflake-managed MCP server in front of a governed multi-agent stack

Any MCP client (Claude, ChatGPT, Cursor, this demo's Streamlit app)
↓
ORCHESTRATOR_MCP: one CORTEX_AGENT_RUN tool, northwind_assistant
↓
ORCHESTRATOR_AGENT
ASK_SALES / ASK_SUPPORT bridges (EXECUTE AS CALLER)
↓
SALES_AGENT → SALES_SEMANTIC_VIEW + row access policy
SUPPORT_AGENT → SUPPORT_SEMANTIC_VIEW
Pattern: the MCP session runs as the signed-in user's default role, every hop below it runs as the caller, and each specialist's grants and the row access policy apply on every call. The client is just a client.

Two identities, exactly as with Claude

The model call

The host app asks a Claude model (claude-sonnet-4-6 on Cortex's Anthropic-compatible /api/v2/cortex/v1/messages) what to do, with a PAT on the presenter's user. This plays the LLM vendor's part and never reads governed data.

The tool call

Each tool_use becomes a JSON-RPC tools/call to the MCP server, signed in as the persona user with a key-pair JWT. That is the identity the orchestrator, the bridges and the row access policy see.

# Same traffic any MCP client sends; the server cannot tell them apart
POST https://<account>.snowflakecomputing.com/api/v2/databases/MULTI_AGENT_MCP_DEMO/schemas/APP/mcp-servers/ORCHESTRATOR_MCP
Authorization: Bearer <persona key-pair JWT>          # Claude Desktop: OAuth
{"jsonrpc": "2.0", "method": "tools/call",
 "params": {"name": "northwind_assistant", "arguments": {"text": "FY25-Q4 bookings by theater?"}}}

The boundary is four layers of grants

No prompt, no application code and no model decision participates

Layer 1
USAGE on the orchestrator and both bridges: everyone may ask
→
Layer 2
USAGE on a specialist: the nested DATA_AGENT_RUN runs as the caller
→
Layer 3
SELECT on the semantic view and its base table
→
Layer 4
Row access policy: rows per caller's role, fail closed
CREATE OR REPLACE PROCEDURE ASK_SALES_SPECIALIST(USER_QUERY VARCHAR)
  RETURNS VARCHAR LANGUAGE PYTHON ...
  EXECUTE AS CALLER   -- the security property: no USAGE on SALES_AGENT -> error 399513 -> NOT_ENTITLED
Under EXECUTE AS OWNER every caller would get the specialist's answer with the owner's privileges, and the row access policy would evaluate the owner role.

One front door: a Snowflake-managed MCP server

CREATE OR REPLACE MCP SERVER MULTI_AGENT_MCP_DEMO.APP.ORCHESTRATOR_MCP
  FROM SPECIFICATION $$
tools:
  - name: "northwind_assistant"
    type: "CORTEX_AGENT_RUN"
    identifier: "MULTI_AGENT_MCP_DEMO.APP.ORCHESTRATOR_AGENT"
    description: "Governed answers about sales bookings and product support..."
$$;
GRANT USAGE ON MCP SERVER ORCHESTRATOR_MCP TO ROLE MULTI_AGENT_MCP_DEMO_SALES_EMEA;  -- and each persona

One tool, no SQL

No SYSTEM_EXECUTE_SQL: every client gets the same single front door, and the persona boundary stays where the grants put it.

Same tool for everyone

tools/list returns northwind_assistant for every persona. The client never learns there are two specialists behind it.

Grants on re-create

There is no ALTER for the specification, and CREATE OR REPLACE drops the server's grants: re-apply them every time.

The alternative: agent toolsets

One agent inherits the specialists' tools at run time

CREATE OR REPLACE AGENT TOOLSET_AGENT FROM SPECIFICATION $$
tools:
  - tool_spec: { type: agent_toolset, name: sales_tools }
  - tool_spec: { type: agent_toolset, name: support_tools }
tool_resources:
  sales_tools:   { agent_name: MULTI_AGENT_MCP_DEMO.APP.SALES_AGENT }
  support_tools: { agent_name: MULTI_AGENT_MCP_DEMO.APP.SUPPORT_AGENT }
$$;

Union at run time

Snowflake checks the caller's USAGE on each referenced agent and merges its tools (sales_analyst, support_kb) into one orchestrator.

Silent skip

No USAGE on a referenced agent: its tools are dropped with no error and no annotation. The refusal wording lives in the toolset agent's instructions.

Bounded fan-out

At most 25 referenced agents and 5 levels per run (CORTEX_AGENT_TOOLSET_MAX_AGENTS, _MAX_DEPTH). TOOLSET_MCP exposes it under the same tool name.

When to use which

Hub and spoke

  • Domains need their own instructions, model, budget or owning team
  • Tool count is large enough that one context degrades selection
  • You want an explicit, auditable denial and one trace per agent
  • Watch: bridge code to maintain, context lost between hops, two or more runs per question

Agent toolset

  • One agent can hold all the tools and still pick well
  • You want native charts and lower latency, one run per question
  • Tools are owned centrally
  • Watch: a missing grant is invisible; one context holds every tool description
Either way the MCP front door is identical: same tool name, same grants underneath, so a client switches architecture by changing one server URL.
