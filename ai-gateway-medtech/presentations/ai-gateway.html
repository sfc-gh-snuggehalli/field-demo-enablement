Why External Agents Need a Control Plane

Sprawl of keys and endpoints

Every team wires its own provider keys into agents, notebooks and apps. Nobody can say which models are in use or who is calling them.

No visibility into agent behaviour

A single agent turn fans out into several model calls and tool calls. Without traces, slow or failing turns are guesswork.

Spend you can't attribute or cap

Token-based billing scales with verbose prompts and runaway outputs. Finance needs per-user and per-team attribution and hard limits.

Optimization without evidence

Prompt and model choices are made by intuition. Teams need a repeatable way to prove a cheaper config keeps answer quality.

Publishing the Agent to Any Client (MCP)

One governed tool: a Cortex Agent behind the MCP server

CREATE AGENT MEDTECH_SALES_AGENT ...        # 2 Analyst tools + product knowledge search + charts

CREATE MCP SERVER MEDTECH_MCP FROM SPECIFICATION $$
tools:
  - name: medtech_sales_agent
    type: "CORTEX_AGENT_RUN"
    identifier: "CORTEX_GATEWAY_MEDTECH_LAB.PUBLIC.MEDTECH_SALES_AGENT"
$$;
No raw SQL tool: the client can't bypass the semantic views. Share-loss scores from the registered XGBoost model and cited field documents reach the client through the same tool. Clients connect over streamable HTTP at /api/v2/databases/<db>/schemas/<schema>/mcp-servers/<name> with the same PAT, and tools execute under the caller's role.
Two layers of orchestration: the external agent decides whether to ask Snowflake; the Cortex Agent decides how to answer. The gateway traces the first; Cortex Agent monitoring covers the second.

What is Cortex AI Gateway?

A governed inference endpoint that Snowflake provisions for you

Inference

OpenAI Chat Completions and Anthropic Messages APIs. Any client that can override its base URL works: SDKs, LangChain, coding agents.

Observability

One OpenTelemetry span per request in AGENT_TRACE_TABLE('SNOWFLAKE'): model, timing, tokens, status, and optionally the full prompt and response.

Cost management

Credits per request in AI_GATEWAY_USAGE_HISTORY, attributed to the calling user. Budgets and per-user quotas apply to the AI GATEWAY domain.

Access control

USAGE to send requests, MONITOR to read traces and usage. Model access still follows Cortex model RBAC.

Not the same as Cortex Inference: /api/v2/cortex accepts the same requests, but only traffic through /api/v2/aigateways/SNOWFLAKE gets the gateway's access control, traces and cost attribution.

One Endpoint, Two Standard APIs

/v1/chat/completions

OpenAI-compatible. All non-Claude models (OpenAI GPT-5 family and others your account can reach).

/v1/messages

Anthropic-compatible. Claude models only. Use a Bearer token, not the SDK's default x-api-key header.

from langchain_openai import ChatOpenAI

llm = ChatOpenAI(
    model="openai-gpt-5.4",
    base_url="https://<account-host>/api/v2/aigateways/SNOWFLAKE/v1",
    api_key=PAT,                                   # programmatic access token
    max_completion_tokens=4096,                     # GPT-5 family: not max_tokens
    default_headers={"traceparent": traceparent},   # groups one agent turn
)
Gotchas seen in the lab: hostnames must use hyphens, not underscores; GPT-5 models reject max_tokens; Claude sent to /chat/completions returns 400.

Every Call is Traced

SELECT TRACE:"trace_id"::STRING                                   AS trace_id,
       RECORD:"name"::STRING                                       AS span_name,
       RECORD:"status":"code"::STRING                             AS status,
       DATEDIFF('millisecond', START_TIMESTAMP, TIMESTAMP)        AS duration_ms,
       RECORD_ATTRIBUTES:"gen_ai.usage.output_tokens"             AS output_tokens,
       RECORD_ATTRIBUTES:"gen_ai.input.messages"                  AS prompt   -- payload capture
FROM TABLE(AGENT_TRACE_TABLE('SNOWFLAKE'))
WHERE TIMESTAMP > DATEADD('hour', -1, CURRENT_TIMESTAMP());

AI diagnosis

claude-sonnet-4-5 reads a per-user, per-model telemetry profile plus sampled captured payloads and returns findings: root cause, evidence span ids, and one testable config change. Each finding seeds an experiment, like the rule findings do.

Prompt optimizer

OPRO/APE-style: proposes candidate system prompts from the weakest answers and the judge's rationales, selects on a dev split, then confirms against the baseline on held-out prompts.

Rubric judge

Correctness 0.5, completeness 0.2, conciseness 0.1, compliance 0.2 (on-label, no superiority claims, no patient data), returned as JSON with a rationale. An optional second judge from another provider (openai-gpt-5.4) reports an agreement score.

Evidence, not intuition: the eval set covers sales metrics, account health, share loss, labeling, evidence, policy and definitions, with expected values computed in SQL from the current data. Every experiment call carries its own traceparent, so each result row links back to its gateway span.

The Optimizer Runs Through the Gateway Too

Every diagnose, propose and judge call is an AI client like any other

Governed

The optimizer calls the Cortex AI Gateway endpoint, so the same model allowlist, USAGE grant and quotas apply to it as to the field agent.

Traced

Each call carries its own traceparent and a conversation id optimizer-<role>-<run>, is logged to OPTIMIZER_CALLS, and appears in AGENT_TRACE_TABLE with its captured payload: the rubric prompt and the JSON verdict.

Costed

The Cost of optimization panel shows the experiment's credits and the payback in days against the projected saving.

SELECT RECORD_ATTRIBUTES:"gen_ai.conversation.id"::STRING  AS conversation,   -- optimizer-judge-<run>
       RECORD_ATTRIBUTES:"gen_ai.usage.output_tokens"      AS output_tokens,
       RECORD_ATTRIBUTES:"gen_ai.output.messages"          AS verdict
FROM TABLE(AGENT_TRACE_TABLE('SNOWFLAKE'))
WHERE conversation LIKE 'optimizer-%';
We ship the evidence, and the evidence has a receipt. The decision to change a prompt or a model is itself traced, attributed and paid for, in the same telemetry as the traffic it optimizes.

Governing Spend: Attribute, Cap, Enforce

Attribute

Every gateway request lands in AI_GATEWAY_USAGE_HISTORY with its credits, model, tokens and calling user. A COST_CENTER tag on users turns that into chargeback by team.

Cap

Budgets track team spend (scoped by the same tag). Per-user quotas set daily, weekly and monthly credit limits on the AI GATEWAY domain, with notifications on actual or projected spend.

Enforce

With block enforcement on, a user at the limit is denied by the platform: HTTP 403, "exceeded the usage quota limit", with the restore time. The block clears at the cycle reset, or 5-10 minutes after the limit is raised.

Enforcement lands within minutes of the spend, not on each request, so a user can briefly overshoot; size limits with headroom. One limit applies to every user in a quota: use a tier tag and a second quota for heavier users.

Admin Controls

ALTER AI GATEWAY SNOWFLAKE FROM SPECIFICATION $$
schema_version: 1
models:
  - name: '*'                     # or an explicit allowlist
logging:
  enabled: true
  enable_client_telemetry: true
  capture_payload:
    request_response: true
$$;                              -- replaces the whole spec

GRANT USAGE   ON AI GATEWAY SNOWFLAKE TO ROLE app_team;      -- send requests
GRANT MONITOR ON AI GATEWAY SNOWFLAKE TO ROLE platform_ops;  -- read traces/usage
Spend controls (budgets, per-user quotas, block enforcement) are covered in Governing Spend.
USAGE is granted to PUBLIC by default. Revoke it to restrict who can send traffic; revoking USAGE is also how a budget action can cut a team off.

When to Use What

AI Gateway

  • External agents, SDKs, coding agents
  • Need traces, attribution, quotas
  • Standard OpenAI / Anthropic clients

MCP server

  • Give any agent governed Snowflake tools
  • Two Analysts, knowledge search and model scores behind one Cortex Agent tool
  • No raw SQL tool to bypass the semantic view

Gateway Tools

  • Connect AI clients to business tools like Glean
  • Admin tool policies (e.g. read-only)
  • Per-user OAuth and tool activity

Cortex Agents

  • Snowflake-hosted orchestration
  • Snowflake Intelligence front end
  • Built-in agent monitoring

Next Steps

1. Turn on logging

Set logging.enabled and capture_payload in the gateway spec, and grant MONITOR to the team that owns observability.

2. Point one agent at the gateway

Swap the base URL of an existing OpenAI or Anthropic SDK client and send a traceparent header per turn.

3. Point Tools at your Glean tenant

Add Glean as a custom server with OAuth, allow only its read-only tools, and grant MCP$USER to a pilot field team.

4. Connect your semantic layer

Model your sales and account health data as semantic views and publish the agent over MCP.

5. Run the optimizer on your eval set

Start from an AI diagnosis, test the change with the rubric judge, and promote only when the confidence interval clears.

6. Add guardrails

Pin the model allowlist, then add a per-user quota with block enforcement and a shared-resource budget per team.

Govern the path, observe every call, and let the telemetry tell you which prompt and model to ship.
