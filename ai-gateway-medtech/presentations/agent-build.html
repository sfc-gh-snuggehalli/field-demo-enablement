Semantic Views: The Business Layer for AI

Define tables, joins, metrics and synonyms once; every agent and BI tool reuses them

CREATE SEMANTIC VIEW ACCOUNT_HEALTH_SV
  TABLES (
    accounts    AS DIM_ACCOUNT PRIMARY KEY (ACCOUNT_ID) WITH SYNONYMS ('hospitals', ...),
    procedures  AS FACT_PROCEDURES ...,            -- every market procedure, ours or a competitor's
    competitive AS FACT_COMPETITIVE_EVENTS ...,    -- evaluations, trials, value analysis reviews
    preds       AS SHARE_LOSS_PREDICTIONS         -- scores from the registered model
      COMMENT = 'Share-loss risk scores from the registered SHARE_LOSS_MODEL' ...)
  RELATIONSHIPS (procedure_to_account AS procedures(ACCOUNT_ID) REFERENCES accounts, ...)
  METRICS (...)                                  -- e.g. procedure share, at-risk accounts

SALES_PERFORMANCE_SV

Net revenue, units, ASP, discount, quota attainment, contracts and price tiers, consigned inventory.

ACCOUNT_HEALTH_SV

Procedure share vs competitors, competitive events (evaluations, trials, value analysis reviews, conversions, win-backs), complaints, physicians and KOLs, share-loss risk.

Both views ship with verified queries, so the most common field questions resolve to known-good SQL.
Why it matters for governance: Cortex Analyst only writes SQL against what the semantic view exposes, and the SQL runs under the caller's role. The semantic view is the boundary the agent can't step outside.

The field's rule of thumb

Upcoming renewal + complaints + competitor trials flags about 186 of 300 accounts, against a real loss rate of about 29%. Holdout ROC AUC 0.67.

The registered model

Learns from H1 share and trend, evaluations and trials, complaints, days to renewal, discount, KOLs and expiring consigned stock. Holdout ROC AUC 0.78 in our validation run.

The payoff: a rep asks "which of my accounts are at risk?" and the agent answers from model scores, not a rule that flags most of the territory, with no model endpoint or feature export outside Snowflake.

The agent is the contract

Tools, tool descriptions and orchestration instructions live in one CREATE AGENT spec. Add or change a tool there and every front end picks it up; no client code changes.

Many front ends, one agent

The same agent serves Snowflake Intelligence, the Agent REST API, and external clients over MCP (see the AI Gateway deck). Built-in agent monitoring records each run.

Compliance in the instructions

On-label answers only, no clinical superiority claims versus competitors, and no patient data. Clinical questions outside labeling are referred to Medical Affairs.

Sample question: "Which Northeast accounts have the highest share-loss risk, and what does our clinical evidence say against the competitor they are trialing?" The agent combines account_health_analyst for risk and competitive events with product_knowledge_search for the evidence summary and battlecard.

Actions are stored procedures exposed as tools, governed the same way as reads

4. Notify

-- Illustrative: not deployed by lab/setup.sql
CREATE PROCEDURE CREATE_INVENTORY_ROTATION_REQUEST(from_account STRING, to_account STRING, sku STRING, units INT)
  RETURNS VARIANT LANGUAGE SQL EXECUTE AS OWNER ...  -- validates inputs, INSERTs rows with STATUS='PENDING_APPROVAL'

# Agent spec: same proc as a custom tool        # MCP spec: or expose it directly to MCP clients
- tool_spec: { type: generic,                    - name: create_rotation_request
    name: create_rotation_request, ... }           type: "GENERIC"
tool_resources:                                    identifier: "...PUBLIC.CREATE_INVENTORY_ROTATION_REQUEST"
  create_rotation_request:                         config: { type: "procedure", input_schema: ... }
    type: procedure, identifier: ...

Write back in Snowflake

Queue an inventory rotation, flag an account for a win-back visit, open a follow-up row for a complaint. The proc owns the write; the agent never gets raw DML.

Reach outside Snowflake

The same proc can send email through a notification integration (SYSTEM$SEND_EMAIL) or call a CRM or ticketing system through an external access integration.

Keep a human in the loop

Write to a PENDING_APPROVAL state and let a person or a downstream task release it. Return the request id so the agent can report what it did.

Guardrails: grant USAGE on the procedure only to roles allowed to act; validate and cap every argument inside the proc (prompt injection can shape inputs); put write tools on the agent rather than adding SYSTEM_EXECUTE_SQL; log each action to an audit table from inside the proc.
