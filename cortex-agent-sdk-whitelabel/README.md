# Building Agentic AI Applications on the Cortex Agent SDK

[View Presentation](https://sfc-gh-snuggehalli.github.io/field-demo-enablement/cortex-agent-sdk-whitelabel/presentations/cortex-agent-sdk-whitelabel.html)

How to build a fully branded, CoWork-style agentic application on top of the **Cortex Agent SDK** and governed Cortex Agents, generated from a single meta-prompt with a high-reasoning model in Cortex Code. The reference app, **ACME Assist** for the fictional ACME Retail, includes:
- streaming chat with a custom animated logo
- an embedded browser whose apps the agent drives through client-side tools
- approval cards for write actions
- a Power Mode backed by the Cortex Code sandbox
- a Studio mode for document and app generation
- deploy paths to Docker, Snowpark Container Services and Snowflake App Runtime

## Audience

Solution engineers, architects and app developers who want to ship a branded agent experience to their own users or customers.

## Topics Covered

- The Cortex Agent SDK (`@snowflake/cortex-agent-sdk`): runs, threads, runs reconnect/cancel, auth, Cortex Code sessions
- The meta-prompt pattern: seed prompt, then clarifying questions, then a full build spec, then a one-shot build
- Branding by configuration (one `brand.config.ts`, CSS variables, a second sample theme)
- Client-side tool execution (`generic` tools, `client_side_execute`, `tool_result`, `permission_decision`)
- Power Mode with `code_toolset_all` and `always_ask` approvals
- Resumable runs, server-side history, SSO identity and caller's rights
- Deploying to Docker, SPCS and Snowflake App Runtime

## Hands-On Lab

### Prerequisites

- Snowflake account with Cortex Agents and Cortex Analyst; SYSADMIN for objects and ACCOUNTADMIN for role grants
- Node.js 22.22 or later
- Snowflake CLI with `app.yml` version 2 support (3.29 verified) for the App Runtime deploy, or [uv](https://docs.astral.sh/uv/) (`brew install uv`): without `snow` on PATH, `setup.sh` runs the CLI through `uvx` with no separate install (the App Runtime deploy still needs `snow` installed)
- A programmatic access token (PAT) for local runs
- Docker, only for the Docker and SPCS paths
- Cortex Code with a high-reasoning model, only for the live one-shot build
- The Cortex Agent SDK is in Preview: pin `@snowflake/cortex-agent-sdk@0.0.1`

### Setup

**Quick start:** after cloning, run one script. It checks prerequisites, creates and seeds the Snowflake objects, grants the demo role to your user, writes `app/.env`, runs `npm install` and runs the client-side tool smoke test:

```bash
cd cortex-agent-sdk-whitelabel
./setup.sh                 # prompts for a Snowflake CLI connection and a PAT file
cd app && npm run dev      # http://localhost:5173
```

Flags: `-c <connection>` with `-p <pat-file>` or `--create-pat` (non-interactive; `--create-pat` creates a 7-day PAT restricted to `ACME_DEMO_ROLE`), `--history` (Snowflake history store), `--skip-npm`, `--force-env`, `--teardown [--yes]`. The connection's user needs SYSADMIN and ACCOUNTADMIN. After setup, everything is an npm script in `app/` (see [Run the app](#run-the-app)).

**With Cortex Code:** open this repository in Cortex Code and paste:

```text
Set up the Cortex Agent SDK demo in the cortex-agent-sdk-whitelabel folder on my Snowflake account.
1. Check Node.js is 22.22 or later. If neither snow nor uv is installed, ask me before
   installing uv (brew install uv).
2. Run ./setup.sh </dev/null (always add </dev/null so it never waits for typed input).
   When it stops and names a flag, show me the options it printed (point out the
   connection marked is_default), ask me which to use (for the PAT: an existing file
   with -p, or --create-pat), and re-run with those flags.
   If I have no Snowflake CLI connection, help me create one with snow connection add.
3. Judge progress by the lines starting with ==> or ERROR:. If sign-in seems stuck, tell
   me to finish it in the browser, then re-run the same command.
4. When it prints Done (after a PASS from the smoke test), start cd app && npm run dev in
   the background and give me http://localhost:5173.
Do not run --teardown or deploy unless I ask.
```

**Manual setup:** run in order with a SYSADMIN connection:

```bash
snow sql -f lab/setup.sql        # objects + semantic view + agents (re-run after seeding if first time)
snow sql -f lab/seed_data.sql    # seed rows
snow sql -f lab/history.sql      # optional: HISTORY_STORE=snowflake
```

On a first run, `setup.sql` creates the tables, then you load `seed_data.sql`. The file is idempotent, so re-running it after seeding builds the semantic view and agents over populated data. It creates:
- `ACME_ASSIST_DEMO` with schemas `DATA` and `APP`, and the `ACME_ASSIST_WH` warehouse
- the tables REGIONS, PRODUCTS, INVENTORY, DAILY_SALES, ORDERS, FULFILLMENT_EXCEPTIONS and REGION_RISK
- the `ACME_SEMANTIC_VIEW` semantic view
- the `ACME_ASSIST_AGENT` agent (Cortex Analyst plus charts)
- the `ACME_POWER_AGENT` agent (`code_toolset_all` with `always_ask`, plus Cortex Analyst)
- the `ACME_DEMO_ROLE` role, plus `ACME_HISTORY_ROLE` from `history.sql`

### Run the app

```bash
cd app
cp .env.example .env             # set SNOWFLAKE_ACCOUNT, SNOWFLAKE_PAT_FILE, role, warehouse
npm install
npm run dev                      # http://localhost:5173 (proxy on :8080)
VITE_BRAND=northwind npm run dev # same app, second brand
```

Useful checks:
- `npm run spike`: client-side tool round trip against your account
- `npm run test:scenarios`: the three end-to-end scenarios against the live agent
- `npm run check:identity`: auth and isolation
- `npm run build`: production bundle and chunk report

### Deploy

| Target | Command |
|---|---|
| Docker | `docker compose up` (serves http://localhost:8080) |
| SPCS | `app/snowflake/spcs/setup.sql`, then `npm run deploy:spcs` |
| Snowflake App Runtime | `npm run deploy:sar` (syncs into `app-runtime/`, then runs `snow app deploy`) |
| Studio runner | `STUDIO=http://coco-runner:8790 docker compose --profile coco up` |

### Build it yourself (one-shot)

1. Open a fresh Cortex Code session on a high-reasoning model.
2. Attach `PROMPT.md` and say: *"Build the application described in PROMPT.md. Follow it exactly, starting with the Step 0 client-side tool spike, and stop to ask me before any deploy."*
3. To target another brand or domain, start from `META_PROMPT.md` instead.

## Key Concepts

- **Client-side tools:** a `generic` tool with no `tool_resources` makes the agent emit `tool_use` with `client_side_execute: true`. The app executes it and returns a `tool_result` on the same thread.
- **Named agent plus per-request tools:** named-agent runs don't accept extra request tools. The proxy calls `client.agent.describe` once and runs the governed spec through `client.agent.stream` with the browser and MCP tools merged in.
- **Resumable background runs:** each turn starts as an Agent API background run (`client.agent.run({ stream: false, background: true })`, which works on the lite endpoint with client-side tools) and is read with `client.runs.stream(runId, { startingAfter })`. The proxy maps upstream `sequence_number`s onto its own cursor and persists the run record, so a reload, a server restart or another instance can resume the answer from Snowflake; Stop calls `client.runs.cancel`.
- **Data-relative dates:** seed data is generated relative to an anchor date (default: the day you run `gen:seed`), and the proxy reads MAX(order_date) at startup to tell the agent "Data current as of <date>".
- **Production hygiene:** request ids and structured logs without prompts, per-user rate limits, upstream retries with backoff, graceful SIGTERM drain, a self-only CSP, and MCP auth headers held server-side (never in the browser).
- **Power Mode:** `code_toolset_all` with `always_ask` turns every state-changing sandbox action into an approval card. Call it with caller's rights; the sandbox gets data only through SQL tools.
- **One server, two frameworks:** Fetch-API handlers sit behind thin Express and Next.js adapters, and the same `AppRoot.tsx` runs in Vite and Next.js.
